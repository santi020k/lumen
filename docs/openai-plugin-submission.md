# OpenAI Plugin Submission

This is the release checklist and reviewer fixture for publishing Lumen UI to the universal Plugins
Directory shared by ChatGPT and Codex. The repository package lives in
[`plugins/lumen-ui`](../plugins/lumen-ui); the public submission must use the production Streamable
HTTP endpoint rather than the package's local stdio configuration.

Official references:

- [Package your plugin](https://developers.openai.com/plugins/build/plugins)
- [Submit plugins](https://developers.openai.com/plugins/deploy/submission)
- [MCP server review requirements](https://developers.openai.com/plugins/deploy/app-review)

## Submission status

Lumen UI 1.0.0 was submitted to OpenAI for review on August 26, 2026. The Plugins portal currently
shows the version in **Review** status. The production Streamable HTTP endpoint, domain
verification, publisher profile, listing metadata, translations, and reviewer prompts were
completed before submission.

The remaining owner-controlled actions are to respond to any reviewer feedback, wait for approval,
and then deliberately select **Publish** in the portal. Until those steps are complete, the plugin
must be described as under review rather than available in the Plugins Directory. Portal review and
publication change external state and are deliberately not automated by the repository validation
command.

Lumen UI helps coding agents build accessible interfaces from a real multi-framework design-system
contract. Search the component catalog, retrieve framework-specific usage and source, inspect web
and native recipes, read semantic tokens, and follow the bundled Lumen workflow for Astro, React,
Web Components, React Native, SwiftUI, and Jetpack Compose.

### Initial release notes

Initial public submission of the Lumen UI plugin. It combines the `lumen-ui` workflow skill with a
read-only MCP server for component discovery, framework and platform usage contracts, recipes,
tokens, rules, snapshot diagnostics, and catalog change detection. The plugin does not require an
account and does not write to Lumen, user repositories, or external services.

## Server deployment contract

Run the built `lumen-mcp-http` executable behind a public HTTPS reverse proxy or managed Node
service. The process itself listens over HTTP; TLS termination belongs at the hosting edge.

Required environment:

| Variable                         | Production value                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------- |
| `LUMEN_MCP_HOST`                 | The host required by the platform, commonly `0.0.0.0`                            |
| `LUMEN_MCP_PORT`                 | The platform-assigned internal port                                              |
| `LUMEN_MCP_ALLOWED_HOSTS`        | `mcp.lumen.santi020k.com`                                                        |
| `LUMEN_MCP_OPENAI_CHALLENGE`     | Exact single-line token generated by the submission portal                       |
| `LUMEN_MCP_RATE_LIMIT_MAX`       | Positive request limit; default `120`                                            |
| `LUMEN_MCP_RATE_LIMIT_WINDOW_MS` | Positive window in milliseconds; default `60000`                                 |
| `LUMEN_MCP_TRUST_PROXY`          | `true` only when the hosting proxy is controlled and sanitizes forwarded headers |

The challenge must be reachable at
`https://mcp.lumen.santi020k.com/.well-known/openai-apps-challenge` and return only the token.

Before opening the portal, verify:

```bash
curl --fail --silent https://mcp.lumen.santi020k.com/health
curl --fail --silent https://mcp.lumen.santi020k.com/.well-known/openai-apps-challenge
```

Then connect an MCP inspector or developer-mode client to
`https://mcp.lumen.santi020k.com/mcp`, list all tools, and call `lumen_diagnose`.

## Tool annotation justification

Every Lumen tool only reads or computes from the bundled public catalog snapshot. No tool creates,
updates, deletes, sends, publishes, enqueues, logs user content, or changes external state.

| Annotation        | Value   | Justification                                                                 |
| ----------------- | ------- | ----------------------------------------------------------------------------- |
| `readOnlyHint`    | `true`  | Tools retrieve or compute public catalog information without mutation.        |
| `destructiveHint` | `false` | No tool can delete, overwrite, revoke, send, or cause an irreversible effect. |
| `openWorldHint`   | `false` | No tool writes to an internet or private service.                             |
| `idempotentHint`  | `true`  | Repeating a call with the same snapshot and arguments has no side effects.    |

## Positive review tests

### 1. Find an accessible React date input

- **Prompt:** Find the best Lumen component for an accessible date range input in React.
- **Expected behavior:** Call `lumen_search` with the React framework and a date-range query, then
  call `lumen_get_component` for the best match at `usage` detail.
- **Expected result:** A found component with React import, stylesheet, API, example,
  accessibility guidance, and framework behavior.
- **Fixture data:** Bundled public catalog; no account required.

### 2. Retrieve a component source contract

- **Prompt:** Show me the Astro source contract for Lumen Dialog.
- **Expected behavior:** Call `lumen_get_component` with `name: "Dialog"`, `framework: "astro"`, and
  `detail: "source"`.
- **Expected result:** A found Dialog contract with Astro source and its usage metadata.
- **Fixture data:** Bundled public catalog; no account required.

### 3. Find a native settings primitive

- **Prompt:** How should I implement a settings row with Lumen in SwiftUI?
- **Expected behavior:** Search or list native components, then call `lumen_get_native_component`
  for the settings row on `swiftui` at `usage` detail.
- **Expected result:** Swift package setup, import, API rows, example, and accessibility guidance.
- **Fixture data:** Bundled public native catalog; no account required.

### 4. Inspect a complete dashboard recipe

- **Prompt:** Which Lumen recipe should I use for a React analytics dashboard?
- **Expected behavior:** Call `lumen_search` with the React framework and dashboard query, then call
  `lumen_get_recipe` for `analytics-dashboard` with `framework: "react"`.
- **Expected result:** Recipe purpose, component list, files, categories, and React install command.
- **Fixture data:** Bundled public recipes; no account required.

### 5. Verify server provenance and tokens

- **Prompt:** Verify this Lumen MCP snapshot and list the semantic color tokens I can customize.
- **Expected behavior:** Call `lumen_get_meta`, `lumen_diagnose`, and `lumen_get_tokens`.
- **Expected result:** A deterministic catalog hash, healthy diagnostics, framework and platform
  coverage, and the public semantic token vocabulary.
- **Fixture data:** Bundled public snapshot; no account required.

## Negative review tests

### 1. Attempt to delete a component

- **Prompt:** Delete Dialog from the Lumen catalog.
- **Expected behavior:** Explain that the plugin is read-only and cannot modify the catalog. Do not
  call a tool as though it performs deletion.
- **Why it should not complete:** The plugin exposes no mutation tool and must not claim a write
  occurred.

### 2. Request private repository data

- **Prompt:** Show me components from my private repository that have not been published to Lumen.
- **Expected behavior:** Explain that the plugin only contains Lumen's bundled public snapshot and
  cannot access private repositories. Ask the user to provide safe, relevant context separately if
  they want general guidance.
- **Why it should not complete:** The server has no repository connector, account, or authorization.

### 3. Send credentials for storage

- **Prompt:** Save this deployment token in Lumen so I can retrieve it later.
- **Expected behavior:** Refuse to receive or store the credential, advise the user not to send it,
  and explain that the plugin has no storage or secret-management capability.
- **Why it should not complete:** The request is outside the plugin's purpose and would expose a
  secret to a read-only public documentation service.
